# Git в VS Code и терминале

## Три удобные возможности VS Code

1. Source Control (Ctrl+Shift+G) показывает изменённые файлы и позволяет
   выбирать отдельные изменения для индекса, не набирая пути вручную.
2. Встроенный diff показывает старый и новый текст рядом: легче заметить
   лишние изменения перед коммитом.
3. Редактор конфликтов показывает входящие и текущие изменения и помогает
   собрать итоговую версию. GitLens дополнительно показывает автора строки.

## Что удобнее в терминале

Интерактивный rebase: `git rebase -i HEAD~3` позволяет явно задать порядок
коммитов и squash. Эти команды можно повторить на сервере без графического IDE.

# Сравнение Git и SVN

## 1. Почему ветвление в Git называют дешёвым?

Ветка Git — небольшой указатель на коммит. Создание новой ветки локально
не копирует проект и не требует обращения к серверу.
Фраза «ветки SVN всегда дорогие» неточна: серверный `svn copy URL1 URL2`
использует cheap copies, занимает постоянное время и не дублирует всё дерево.
Копирование рабочей папки на клиенте может быть медленным. Отличие SVN —
ветка представлена каталогом репозитория и её фиксация требует доступа к нему.
Источник: [Version Control with Subversion — Using Branches](https://svnbook.red-bean.com/en/1.7/svn.branchmerge.using.html).

## 2. Можно ли сделать коммит SVN без интернета?

Для `svn commit` нужен доступ к репозиторию. Если он на недоступном удалённом
сервере, коммит невозможен; редактирование и часть локальных операций доступны.
Сам интернет не обязателен: сервер может находиться в локальной сети,
а репозиторий на том же компьютере доступен через `file://`.
Git хранит репозиторий локально, поэтому позволяет коммитить офлайн.

## 3. Когда SVN может быть предпочтительнее?

В организации с работающей SVN-инфраструктурой и высокой стоимостью миграции;
при необходимости централизованных прав доступа к отдельным каталогам;
при работе с плохо сливаемыми бинарными файлами, когда нужен процесс с блокировками.
Это зависит от требований команды: Git не делает SVN непригодным автоматически.

## 7. Контрольные вопросы и подготовка к занятию 3



1. **Почему защищают main?** Чтобы изменения проходили проверку до попадания
   в стабильную ветку. Прямые коммиты технически допустимы, но политика команды
   обычно требует PR. Отдельный коммит часто можно отменить через revert;
   невозможность отмены не является общим свойством Git.
2. **GitHub Flow.** Создать ветку от main, сделать коммиты, push, открыть PR,
   получить review, исправить замечания, выполнить merge, удалить feature-ветку.
3. **PR и merge.** PR — предложение изменения с обсуждением и проверками;
   merge — операция объединения истории или изменений. PR может завершиться без merge.
4. **Code Review.** Проверка изменения другим участником: поиск ошибок,
   оценка понятности и обмен знаниями. Авторское самопроверение не заменяет парное review.
5. **Git и SVN.** Git распределённый: локально есть история и коммиты.
   SVN централизованный: коммиты поступают в единый репозиторий.
6. **feat:.** Тип коммита Conventional Commits для новой функциональности.
7. **Первый push.** `git push -u origin feature/hobby-project` публикует ветку
   и задаёт upstream для следующих push/pull.
8. **Зачем CLI?** Он доступен на серверах и в CI, позволяет писать скрипты
   и точно управлять Git без зависимости от интерфейса редактора.

## Merge или rebase?

Merge выбираю для объединения опубликованной работы команды: он сохраняет
историю ветвления и не переписывает существующие коммиты. Rebase выбираю для
своей неопубликованной ветки: переношу её на свежий main или объединяю мелкие
коммиты. Rebase создаёт новые идентификаторы коммитов, поэтому переписывать
общую историю без согласования нельзя.

В упражнении `practice/rebase-playground` три коммита объединены в два через
настоящий `git rebase -i HEAD~3`. Ветка оставлена только локально по заданию.

Источники: [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow),
[Pull requests](https://docs.github.com/en/pull-requests/get-started/about-pull-requests),
