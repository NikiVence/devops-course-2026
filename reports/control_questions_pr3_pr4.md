# ПР3–4: ответы к защите

1. **Merge и rebase.** Merge объединяет линии истории и при настоящем
   слиянии создаёт коммит с двумя родителями. Rebase повторно применяет
   выбранные коммиты к новому основанию и меняет их хеши. Merge удобен для
   общей работы; rebase — для упорядочивания собственной неопубликованной ветки.
2. **Почему опасен rebase общей ветки?** У коллег остаётся старая история,
   идентификаторы расходятся. Понадобится согласованный перенос изменений;
   принудительная отправка может убрать чужие коммиты из ветки.
3. **git rebase -i HEAD~5.** Интерактивно перерабатывает последние пять
   коммитов текущей линии: pick — оставить, reword — изменить сообщение,
   edit — остановиться для правки, squash — объединить с предыдущим,
   fixup — объединить без сохранения текущего сообщения, drop — исключить.
4. **Squash и fixup.** Оба объединяют изменения; squash предлагает собрать
   итоговое сообщение, fixup обычно оставляет сообщение предыдущего коммита.
5. **Cherry-pick.** Переносит изменение отдельного коммита. В ПР3 в main
   перенесён IMPORTANT_FIX, а экспериментальные multiply/divide остались
   в hotfix-ветке.
6. **Reflog.** Локальный журнал перемещений ссылок. После потери ветки
   найти коммит через `git reflog`, проверить `git show <sha>` и создать
   `git switch -c recovered <sha>`. Журнал не бессрочен и не заменяет резервную копию.
7. **Revert и reset.** Revert добавляет новый коммит с обратным изменением,
   сохраняя историю. Reset перемещает указатель ветки; `--hard` дополнительно
   меняет индекс и рабочие отслеживаемые файлы. Для опубликованной работы
   обычно используют revert.
8. **Multi-remote.** Добавить зеркало через `git remote add mirror <url>`.
   Для автоматической отправки через origin явно задать оба push-URL:
   `git remote set-url --add --push origin <основной-url>` и аналогично зеркало.
   Проверить `git remote -v`. Push в два сервера не атомарен: после него
   сравнить `git ls-remote` для обоих адресов.
9. **Upstream.** Обычно это имя remote исходного проекта, а origin — своей
   копии. Имена условные. В ПР4 upstream указывает на Gitverse преподавателя,
   origin — учебную копию в GitHub.
10. **Forking Workflow и GitHub/Gitverse Flow.** В первом случае работают
    через свою копию чужого репозитория и PR к исходнику. Во втором —
    через feature-ветки и PR в своём/общем проекте. В ПР4 импортирован
    исходник с сохранением его истории; PR создан внутри учебной копии.
11. **Git hooks.** Скрипты, запускаемые на этапах операций Git. pre-commit
    может запускать проверку кода; commit-msg получает путь к файлу
    сообщения и проверяет его формат. В ПР3 использован commit-msg.
12. **Конфликт.** Git не выбирает смысл изменений автоматически. Нужно
    прочитать обе версии, составить правильный итог, убрать маркеры,
    выполнить `git add`, завершить merge и запустить проверки.
